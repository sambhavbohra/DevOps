## Overview

When debugging issues in Kubernetes clusters, a systematic command-line workflow is essential. This guide documents the primary diagnostic commands used by DevOps engineers to inspect, debug, and resolve cluster failures.

---

## 1. `kubectl get`

### Purpose
Lists one or more resources of a given type with their high-level operational status, readiness, restart counts, and age.

### Common Syntax and Variations
```bash
# Get pods in the current namespace
kubectl get pods

# Get all resources across all namespaces
kubectl get all -A

# Watch resources update in real time
kubectl get pods -w
```

### Practical Example and Output
```bash
kubectl get pods
```
```
NAME                          READY   STATUS    RESTARTS   AGE
order-service-6f87b8849c-q8kc8 1/1     Running   0          5m
auth-api-79b8849c-2xkl1       0/1     CrashLoopBackOff 4   3m
```

## 2. `kubectl get -o wide`

### Purpose
Extends the standard `kubectl get` table with additional columns such as Pod IP address, the Node on which the pod is scheduled, nominated node, and readiness gates.

### Practical Example and Output
```bash
kubectl get pods -o wide
```
```
NAME                          READY   STATUS    RESTARTS   AGE   IP           NODE       NOMINATED NODE   READINESS GATES
order-service-6f87b8849c-q8kc8 1/1     Running   0          5m    10.244.0.15  minikube   <none>           <none>
auth-api-79b8849c-2xkl1       0/1     Running   0          3m    10.244.0.16  minikube   <none>           <none>
```

## 3. `kubectl describe`

### Purpose
Shows detailed metadata, state, container definitions, resource limits, mount points, and chronological cluster events for a specific resource. It is the single most important command for finding why a Pod is failing to start or schedule.

## 4. `kubectl logs`

### Purpose
Fetches the stdout and stderr streams generated by the containerized application process.

### Useful Flags
- `-f`: Stream logs in real time (follow).
- `--tail=100`: Show only the last 100 lines.
- `-p` or `--previous`: View logs from the previous instance of a crashed container.
- `-c <container-name>`: Specify target container in a multi-container pod.

### Practical Example and Output
```bash
kubectl logs auth-api-79b8849c-2xkl1 --previous
```
```
[2026-10-07 07:45:10] FATAL: Database connection string DB_HOST is not set.
[2026-10-07 07:45:10] Process exited with status 1.
```

## 5. `kubectl exec`

### Purpose
Executes a command directly inside a running container, allowing for live interactive debugging, network ping tests, inspecting filesystem files, and checking local environment variables.

### Practical Example and Output
```bash
# Run interactive bash/sh shell inside pod
kubectl exec -it order-service-6f87b8849c-q8kc8 -- /bin/sh

# Test internal network connectivity from inside the pod
kubectl exec -it order-service-6f87b8849c-q8kc8 -- nc -zv order-db 5432
```
```
Connection to order-db (10.96.120.45) 5432 port [tcp/postgresql] succeeded!
```

## 6. `kubectl events`

### Purpose
Displays cluster events sorted chronologically, highlighting warnings, scheduling decisions, image pulls, volume attachment errors, and probe failures across the namespace.

### Practical Example and Output
```bash
kubectl events --sort-by='.metadata.creationTimestamp'
```
```
LAST SEEN   TYPE      REASON             OBJECT                            MESSAGE
2m          Normal    Scheduled          Pod/order-service-6f87b8849c-q8kc8 Successfully assigned default/order-service to minikube
1m          Warning   FailedMount        Pod/db-pod-1                      MountVolume.SetUp failed for volume "data" : secret "db-credentials" not found
30s         Warning   Unhealthy          Pod/frontend-9f7b-9x              Readiness probe failed: HTTP probe failed with statuscode: 500
```

## 7. `kubectl explain`

### Purpose
Provides inline API schema documentation and field specifications directly in the terminal, showing valid fields, nested types, and expected types without needing a web browser.

### Practical Example and Output
```bash
kubectl explain pod.spec.containers.livenessProbe
```
```
KIND:       Pod
VERSION:    v1
FIELD:      livenessProbe <Probe>

DESCRIPTION:
    Periodic probe of container liveness. Container will be restarted if the
    probe fails. Cannot be updated. More info:
    https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle#container-probes

FIELDS:
    exec    <ExecAction>
    httpGet <HTTPGetAction>
    tcpSocket <TCPSocketAction>
    initialDelaySeconds <integer>
    periodSeconds       <integer>
    timeoutSeconds      <integer>
    failureThreshold    <integer>
```

## 8. `kubectl top`

### Purpose
Displays real-time CPU and Memory utilization for nodes and pods, requiring the `metrics-server` addon to be active in the cluster.

### Practical Example and Output
```bash
kubectl top nodes
kubectl top pods
```

## Diagnostic Workflow Cheat Sheet

```
1. Is Pod running?
   ├── No  --> kubectl get pods -o wide (Check STATUS: Pending, ErrImagePull, CrashLoop)
   │           └── kubectl describe pod <name> (Check Events section)
   │               └── kubectl logs <name> --previous (Check fatal runtime errors)
   │
   └── Yes --> Is Service routing traffic?
               ├── No  --> kubectl get endpoints <service-name> (Check for 0 endpoints)
               │           └── kubectl describe svc <service-name> (Verify selector labels)
               └── Yes --> kubectl exec -it <name> -- curl/nc (Test internal connectivity)
```
